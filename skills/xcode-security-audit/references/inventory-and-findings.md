# Inventory and findings

## Discover the build graph

Prefer repository documentation and project-generation configuration over
guessing from filenames. Use native Xcode project tools when available. Use
Xcode through computer use when its navigator or settings editor exposes the
answer faster. The portable command-line path is:

```bash
xcodebuild -version
xcodebuild -list -json -workspace <Workspace.xcworkspace>
xcodebuild -workspace <Workspace.xcworkspace> -scheme <Scheme> \
  -configuration <Configuration> -destination <destination> \
  -showBuildSettings -json
```

Keep the repository source unchanged during an audit. Record the initial Git
status before opening the project or running `xcodebuild`, and compare it after
each inspection step. Xcode and `xcodebuild` can resolve Swift packages while
loading a project. Put Derived Data and cloned packages outside the repository,
and use the active toolchain's package-resolution controls:

```bash
xcodebuild ... \
  -derivedDataPath <outside-repository> \
  -clonedSourcePackagesDirPath <outside-repository> \
  -disableAutomaticPackageResolution \
  -skipPackageUpdates
```

When the repository contains a committed `Package.resolved`, also use
`-onlyUsePackageVersionsFromResolvedFile`. If the project cannot load without
creating or changing resolution state, inspect an isolated checkout or leave
the affected value unresolved. Apply the same Git-state guard when using Xcode
through computer use. Remove only files created by the audit; never discard
pre-existing user changes.

Use `-project <Project.xcodeproj>` when the project has no workspace. Select an
actual destination because SDK and architecture conditions can change effective
values. Inspect `xcodebuild -help` on the active toolchain before relying on an
option. Apple documents the build system in its
[Xcode build-system guide](https://developer.apple.com/documentation/xcode/build-system).

Query each relevant scheme, configuration, and destination. The JSON output
groups effective settings by target. Save large output outside the repository
or in an ignored task directory, and extract only the settings and target
identity needed for the report.

Do not pass build-setting overrides while auditing: command-line values can
mask the repository's result. For project targets that are not represented by a
shared scheme, query `-target <Target>` with its configuration and SDK. Keep
three evidence layers distinct:

1. **Declared:** project, generator, and `.xcconfig` assignments.
2. **Effective:** Xcode's resolved values for one target, configuration, SDK,
   and destination.
3. **Built:** diagnostics, architecture slices, and signed entitlements in the
   produced artifact.

For each target, record:

- product type and supported platforms;
- configurations and inherited `.xcconfig` chain;
- source languages actually compiled by the target;
- `CODE_SIGN_ENTITLEMENTS` and the resolved entitlement file, if any;
- source-built and binary dependencies;
- whether the project is generated by Swift Package Manager, XcodeGen, Tuist,
  Bazel, or another tool.

For an XCFramework, inspect its `Info.plist` library variants and architectures.
For the exact framework or archive selected by a build, use
`xcrun lipo -archs <binary>`. Do not update dependency pins during an audit.

When a current representative product exists, inspect its signed entitlements
with `codesign -d --entitlements :- <product>` and correlate them with the
effective build settings and source plist. If no current artifact is available
and producing one is outside the audit, mark built entitlement state unresolved.

Read `.pbxproj` and `.xcconfig` files only after the effective value is known,
to locate the setting's owner and inheritance path. Apple explains configuration
file composition and conditional assignments in
[Adding a build configuration file](https://developer.apple.com/documentation/xcode/adding-a-build-configuration-file-to-your-project).

## Audit the relevant surfaces

Use the active Xcode's
[Build settings reference](https://developer.apple.com/documentation/xcode/build-settings-reference)
as the catalog. Do not carry a fixed list across Xcode versions without checking
that the installed toolchain recognizes each setting.

Review these groups:

1. **Suppression and strictness.** Find target or configuration overrides that
   suppress warnings or weaken language diagnostics. Account for generated and
   third-party code before recommending a project-wide escalation.
2. **Security compiler warnings.** Inspect `ENABLE_SECURITY_COMPILER_WARNINGS`
   and the effective warnings it controls. Apple describes it as a collection
   of bounds- and lifetime-safety diagnostics.
3. **Static analysis.** Run the project's Analyze action for C-family targets
   when practical. Review relevant `CLANG_ANALYZER_SECURITY_*` settings.
   `RUN_CLANG_STATIC_ANALYZER` adds analysis to every build, so treat that as a
   build-time policy choice rather than an automatic audit fix.
4. **Enhanced Security.** Inspect `ENABLE_ENHANCED_SECURITY`, the values it
   cascades, and the hardened-process entitlement family for executable targets.
   Load the Enhanced Security reference before recommending adoption.
5. **Advanced memory safety.** Report C bounds safety, hardware memory tagging,
   and checked pointer arithmetic separately. They can reject existing source
   or change runtime failure behavior. During Enhanced Security adoption,
   `ENABLE_CPLUSPLUS_BOUNDS_SAFE_BUFFERS` belongs to that capability's staged
   C++ work unless the target records a scoped opt-out.
6. **macOS Hardened Runtime.** Inspect `ENABLE_HARDENED_RUNTIME` and any
   exception entitlements separately from Enhanced Security. An exception may
   be required, but it weakens one runtime protection and needs a rationale.

Experimental analyzer settings may have a higher false-positive cost. Label
them experimental and keep them out of the default adoption batch. The build
settings reference identifies
`CLANG_ANALYZER_SECURITY_BUFFER_OVERFLOW_EXPERIMENTAL` as experimental.

## Report findings

Use one row per distinct effective result:

| Target / configuration | Finding | Effective source | Recommendation | Risk and proof |
| --- | --- | --- | --- | --- |

Separate confirmed values from values you could not resolve. Summarize already
active protections, proposed compatible changes, documented exceptions,
undocumented opt-outs, unsupported settings, and advanced follow-ups.

An audit is complete when every in-scope target and configuration is accounted
for and every recommendation names its validation step. Do not grade the whole
project from one scheme's Debug settings.
